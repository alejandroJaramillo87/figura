# Architecture

The machinery that turns one HTML file per diagram into a fragment a consumer inlines or
copies: the embed markers, the managed blocks, the scripts that build and check them, the
static exports, the manifest and the gallery. Every mechanism here follows from one constraint: the blog drops each fragment
verbatim into a busy page, possibly twice. The rules a diagram must follow live in
[.styles/DIAGRAM_STYLE.md](../../.styles/DIAGRAM_STYLE.md); this document explains the
machinery behind them.

## One file per diagram

Each diagram is one self-contained HTML file under `diagrams/<consumer-dir>/<kebab-name>.html`,
built from a static SVG (authored, never generated at runtime), scoped CSS in a `<style>` tag
and vanilla JS in a single IIFE.

The file is also a standalone page that opens directly in a browser. Its `<head>` links
`shared/preview.css` for page chrome, and its body carries a title and a one-line description.
A consumer reads only the region between the embed markers:

```html
<!-- fg:embed-start -->
<div class="fg-diagram fg-<diagram-name>"> ... </div>
<!-- fg:embed-end -->
```

Everything the diagram needs at embed time (styles, markup, script) lives inside that fragment.
Everything outside it, including the `preview.css` link, exists only for standalone viewing.
Once inlined, ids and keyframe names are document-global and the script runs in the page's
scope, so the [hard rules](../../.styles/DIAGRAM_STYLE.md#hard-rules) on scoping and naming are
what keep two diagrams, or two copies of the same diagram, from colliding.

The [root README](../../README.md) routes to each directory and what it holds.

## Managed blocks

Every diagram needs the same boilerplate: palette variables, panel styling, control-bar styling,
the step-timeline state machine and more. Hand-copied boilerplate drifts, so the canonical
source of each piece lives once under `shared/runtime/` (the palette block derives from
`shared/tokens.css`), and `scripts/build.js` stamps it into every fragment between sentinel
comments:

```css
/* fg:begin controls-bar v1 */
/* body generated by scripts/build.js */
/* fg:end controls-bar */
```

The list of blocks, what each provides and which blocks each kind requires is in
[DIAGRAM_STYLE.md](../../.styles/DIAGRAM_STYLE.md#managed-blocks). `scripts/lib/fragment.js`
records each block's interface version, the blocks each manifest `kind` requires and the order
they depend on; the validator refuses a stale version, a missing block, a duplicate or a block
placed before one it depends on.

The system has four properties:

- **Idempotent expansion.** `node scripts/build.js` rewrites every block body from its source,
  re-indented to match the begin marker, so a second run changes nothing. `--file <path>`
  limits it to one diagram.
- **Drift detection.** `node scripts/build.js --check` writes nothing and exits nonzero when a
  block body differs from its source, a block name is unknown, or a sentinel is malformed. An
  unclosed or mismatched sentinel fails rather than swallowing the text between. The quality
  gate runs this step, so a hand-edited block cannot land.
- **One edit propagates everywhere.** A change to `shared/tokens.css` or a runtime file, followed
  by `npm run build`, reaches every diagram.
- **Customization goes through hooks.** Blocks expose CSS hook variables that a diagram sets
  outside the sentinels, and anything else diagram-specific also lives outside the blocks.

`shared/snippets.js` holds the effect helpers a diagram copies by hand (`restartAnimation`,
`launchComets`). Everything else executable lives in `shared/runtime/`.

## The scripts

The scripts under `scripts/` share `scripts/lib/fragment.js`, the parsing layer: it splits a
file on the embed markers (`splitEmbed`), finds the root class (`rootClass`), pairs sentinel
blocks (`findBlocks`), renders blocks, lists diagram files and loads the manifest.
`scripts/lib/cli.js` gives every script one strict argument parser, so an unknown flag is a
usage error rather than a no-op. `scripts/lib/report.js` prints the summary line every check
ends with (see [the quality gate](../testing/quality-gate.md#the-report-line)).

- **`scripts/new-diagram.js`** (`npm run new`) scaffolds a diagram. It validates every input
  before writing (kebab-case path, known kind, an abbreviation no other diagram uses, a free
  manifest id), fills `templates/<kind>.html`, expands the managed blocks in memory through
  `build.js`, and appends a `manifest.json` entry with a TODO description, replacing the
  manifest atomically.
- **`scripts/build.js`** (`npm run build`) is the block expander described above.
- **`scripts/validate.js`** (`npm run validate`) is the contract linter. Its `RULES` table
  declares every rule id it reports, and [the quality gate](../testing/quality-gate.md#validator-rules)
  lists them.
- **`scripts/export-svg.js`** (`npm run export`) writes every static diagram to
  `exports/<slug>/<name>.svg`, described below.

The scaffolder accepts `--palette`, and `fragment.js` keeps palette maps, but only `classic` is
wired. One dark palette is deliberate: diagrams never switch theme.

## Static exports

A consumer that cannot inline HTML or run script references a static diagram as an image. The
export is lossless because the static kind forbids script, SMIL and CSS motion: what remains is
markup plus scoped style, and both survive inside an `<svg>` loaded through `<img>`.

`export-svg.js` moves the fragment's `<style>` inside an outer `<svg>` that carries the root
class, so every scoped selector still matches; a `<rect>` supplies the panel the root `<div>`
supplies in the blog, and the body is translated in by the panel padding. HTML named entities
become numeric references, and every export passes a well-formedness check before it is
written. The output is deterministic and `exports/` is committed, so a diagram edit shows its
image diff in the same pull request. `node scripts/export-svg.js --check` fails when a
committed export is stale. How the consumer takes the file is in
[docs-site.md](../consumers/docs-site.md).

## The manifest

`manifest.json` is a flat array indexing every diagram:

```json
{ "id": "kv-cache-fill",
  "path": "diagrams/inference-loop/kv-cache-fill.html",
  "title": "KV cache fill during the decode loop",
  "kind": "step-timeline",
  "consumers": ["curiosity-chronicles:content/posts/diagram-test.md"],
  "description": "..." }
```

`kind` is one of `step-timeline`, `hover-inspect`, `toggle`, `ambient` or `static`. It selects
the managed blocks the diagram must carry, and `static` also enables the static rules and is
what `export-svg.js` selects on. `consumers` lists every page that embeds or copies the
diagram, as `<repo>:<path>`, so a change can be traced to whoever must pick it up; it is empty
for a diagram nothing uses yet. The validator holds the manifest and `diagrams/` to each other
(the `manifest`, `manifest-id` and `title` rules), and `npm run docs` renders the diagram
catalog in [diagrams/README.md](../../diagrams/README.md) from the entries.

## The gallery

`index.html` is a dependency-free page that fetches `manifest.json`, extracts each file's embed
fragment with the same marker convention, injects the markup and re-creates the `<script>`
nodes so they execute. An HTTP error or a script that throws while embedding shows on that
entry. The gallery renders the first manifest entry twice, a standing check for the collisions
a post that embeds one diagram twice would create. The manifest fetch fails under `file://`, so
the gallery is served over HTTP (see [previewing](../development/workflow.md#previewing)).
